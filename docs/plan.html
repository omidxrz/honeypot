Zero-Day Capture Honeypot

An internet-facing sensor that logs every port, serves a plausible internal admin surface, and runs real vulnerable appliances so an in-the-wild exploit actually fires and leaves evidence. Phases 0 through 2 are built and collecting; phase 3 is held back for want of an isolation layer.

What it is for

Two goals that pull in opposite directions, so they get built as two tiers on one box rather than blended into one confused service.

TierQuestion it answersCostRisk
1 · Catch-all What ports and payloads is the internet probing that I did not know existed? An evening Near zero — nothing executes
2 · Real appliance Is someone burning an unpublished exploit on this product right now? Days, plus a VM host High — the box is meant to be owned

Tier 1 catches volume and novelty. Tier 2 catches intent. A static fake page catches neither, because a zero-day fired at static HTML returns a 200 and produces no signal at all. That is the whole reason the plan escalates past bait.

Non-negotiables

  • Nothing shared with hunting infrastructure. Own domain, own key, own account. No repo access, no credentials that work anywhere else, nothing that identifies the operator.
  • Egress default-deny. Allow only the log sink and DNS. Outbound 25 stays blocked or the provider null-routes the host within days.
  • Cloud metadata blocked. Drop 169.254.169.254 at the firewall before anything listens.
  • The password in chat is now burned. Install a key, disable password auth, rotate the root password as the first action on the box.
  • Collect only what arrives. No counter-probing sources. Harvested credentials are counted, never reused. No personal data leaves the box.
Phase 0

Take the box safely built

Every later phase redirects all TCP traffic into a honeypot listener. If SSH is still on 22 when that rule loads, access to the host is gone permanently. Relocate it and prove the new port works before touching anything else.

  1. Dedicated key installed, password authentication disabled, root password rotated. The key is used for this host only.
  2. sshd moved to 61022 through a drop-in under /etc/ssh/sshd_config.d/, with port 22 kept alive until the new port was proven, then dropped.
  3. nftables baseline: inbound accept, which the honeypot needs, and outbound default-drop with loopback, established, DNS, NTP and ping allowed. Verified from the box that outbound HTTPS fails, DNS resolves, the metadata address is unreachable and outbound 25 is blocked.
  4. Still outstanding: a provider-side snapshot of the clean state, which cannot be taken from inside the guest.

The lockout this prevents is not hypothetical

The first attempt at this box ran ssh.socket alongside a live ssh.service. Restarting the socket handed port 22 to the socket-activated path, whose per-connection sshd died immediately on that image. Connections were accepted and then closed before the banner, on both the old and the new port, and the box had to be rebuilt. Both risky steps in the rebuild ran behind a timed auto-rollback that was cancelled only after access was re-verified.

Phase 1

All-port catch-all built

Sixty-five thousand ports, one socket. Emulating services is not the job; recording what arrives is. A NAT rule redirects every TCP port except SSH into a single listener, which recovers the port the attacker actually aimed at and logs the opening bytes.

/etc/nftables.conf — as deployed

table ip nat {
  chain prerouting {
    type nat hook prerouting priority dstnat; policy accept;
    iif "lo" return
    tcp dport { 61022, 80, 443, 8000 } return
    tcp dport 1-65535 redirect to :8000
  }
}

The listener reads the original destination with SO_ORIGINAL_DST, records peer address, intended port, byte count and the first four kilobytes, then closes. About a hundred and eighty lines of standard library Python, no framework, no dependency. Connections beyond three hundred concurrent are dropped rather than queued.

The server-speaks-first problem

HTTP, TLS, Redis and Memcached send data immediately, so their payloads arrive for free. SSH, SMTP, FTP, MySQL and POP3 wait for a banner and give nothing if none comes. Fix it with a wait, not with emulation: stay silent 1.5 seconds, and if the client has not spoken, emit a banner from a small port-to-banner map, currently fifteen entries covering FTP, SSH, Telnet, SMTP, POP3, IMAP, MySQL, VNC and friends, then log the response. That one map converts dead connections into complete attack samples.

TLS

A large share of interesting traffic is wrapped. First byte 0x16 hands the connection to a terminator with a self-signed certificate, and the plaintext is logged behind it. The bonus is a JA4 fingerprint per connection, which identifies the attacker's tooling — often more useful than the payload itself, because one fingerprint across many ports is a sweep while one fingerprint on one strange port is a targeted probe.

UDP is log-only, permanently

Capture with a packet ring buffer and reply to nothing. Any UDP response turns the host into a DDoS reflector — DNS, NTP, memcached and SSDP amplification all start with a honeypot that answered politely.

Phase 2

Web surface and the decoy console built

Ports 80 and 443 come off the catch-all and get their own stack, because web is where payload variety lives. Nginx logs structured JSON per request, including the body.

nginx log format

log_format hp escape=json '{"t":"$time_iso8601","ip":"$remote_addr","m":"$request_method",'
  '"u":"$request_uri","h":"$http_host","ua":"$http_user_agent","ref":"$http_referer",'
  '"xff":"$http_x_forwarded_for","ct":"$http_content_type","len":$request_length,'
  '"body":"$request_body"}';

The login accepts anything

Commodity scanners stop at a wall. The value of an admin-panel decoy is the traffic after the wall — object references, traversal attempts, template fields, webhook URLs. So any POST to the login sets a session cookie and redirects to the dashboard, with no credential check and nothing executing. Submitted credentials are logged as their own corpus.

The shell

Built on Bootstrap Admin Template. It ships as Vite sources rather than flat HTML, so it needed Node 22 and a real build; the toolchain was then deleted from the host, leaving 3.4 MB of static output. Four changes turn it into a decoy:

  • Self-host every asset. Strip the content-delivery and font references so the panel does not phone out and does not break when egress is denied.
  • Remove the template identity. Its own name, demo links and author credits are what make a panel read as scenery. Rename the product, shift the palette, rewrite the navigation labels toward a security console.
  • Keep the charts, hardcode the data. They ship with static arrays already. Fake event counts and fake internal host names, never real infrastructure and never a real company.
  • Delete every script that fetches. The panel must be inert HTML, CSS and rendering JavaScript only.

Bait surface

The decoy presents as an internal security console: fake event tables, fake host names, a static chart. It is attractive precisely because an attacker who lands on a monitoring panel assumes high value and spends real effort. Every path advertises an attack shape, and the parameter mutations are the product.

PathInvites
/dashboard/events?id=8841Object reference tampering, SQL injection
/dashboard/export?file=events.csvPath traversal, local file inclusion
/dashboard/integrationsServer-side request forgery, via a webhook URL field

Every response is static. In particular the template-injection bait must have no template engine behind it, and the upload endpoint must never write to a served path. The decoy is scenery with instrumentation, not an application.

Two rules on the decoy

  • Generic branding only. Never clone a real company's admin interface, name or logo. That is impersonation regardless of intent.
  • The decoy never reads real data. One symlink into the log directory hands attackers the operator's own addresses and targets. Separate process, separate root, one-way data flow.
Phase 3

Real appliance, instrumented blocked

This is the tier that can catch an unpublished exploit, and it works by running the genuine product and letting it fall. Candidates are whatever is currently being hit: Ivanti Connect Secure, Citrix NetScaler, Fortinet, Palo Alto GlobalProtect, SonicWall, Confluence, Jenkins, GitLab, vCenter. Start with two or three, never twenty.

The signal is post-exploitation

A zero-day request looks like ordinary traffic, so watching the wire alone proves nothing. The evidence comes from inside the guest:

  • Kernel-level tracing on process execution, file writes and outbound connections.
  • Full packet capture with TLS keys logged, so the session preceding an execution event can be read in plaintext.
  • Snapshot and revert on a timer. Each snapshot diff is a self-contained evidence package.

Telling a zero-day from an N-day

The test is exploitation that succeeded while matching no known signature for that product version. Maintaining a signature set for the known bugs is what makes the novel case surface by exclusion — otherwise every hit looks new.

Discovery

These attackers scan by product fingerprint, so appearing on internet-wide scan data with a genuine appliance banner is enough. A plausible hostname and a certificate in the transparency logs accelerate it.

Blocked, and why it stays blocked here

Compromise is the intended outcome, so the guest needs an isolation layer that this host cannot provide. Two virtual CPUs, 3.8 GB of memory and no nested virtualization, which means a container escape lands directly on the machine holding the capture logs and the operator panel. This phase needs either a second box that runs nothing but the guest, or a provider offering nested virtualization with snapshot and revert. Until then every containment rule from Phase 0 is holding a decoy that executes nothing, which is a much easier promise to keep.

Operator panel

Bound to loopback and reached over an SSH forward, never exposed. No database and no server framework: a systemd timer runs the rollup into a JSON file, and one static page renders it with hand-written SVG bars. The rollups that matter are the ones about novelty, not volume.

  • First-seen port. A port that never appeared before, appearing now, is the signal being hunted.
  • First-seen payload shape per port, normalized so that hex, identifiers and timestamps are stripped — novel structure, not novel randomness.
  • Port against payload. A familiar exploit body arriving on an unexpected port means someone found the service on a nonstandard deployment.
  • Fingerprint against payload. Separates broad sweeps from targeted probes.
  • Execution events from Phase 3, joined to the session that caused them.
Analysis

Rules do the work, the model reads the residue

The output is roughly ninety-nine percent repeated commodity noise. Deduplicate and normalize first and the daily unique set collapses to tens of samples, which is a readable quantity. Detection stays deterministic — first-seen port, first-seen shape, execution fired — because a counter that knows a thing is new beats a model that thinks it is interesting. Near-duplicate grouping is a similarity hash, not inference.

first six minutes of exposure

Eighty-one connections from thirty-eight sources across twenty ports, before the host appeared in any scan index. The novel feed already separated identified survey traffic, Palo Alto Cortex Xpanse and internet-measurement.com among them, from protocol probes worth reading: SIP OPTIONS sweeps, an MQTT CONNECT, a Kafka client handshake, RTSP, NTLMSSP negotiation and VNC option strings. That mix is the argument for the banner map. Most of those protocols say nothing until spoken to first.

A language model earns its place on the residue only: the handful of daily samples that survive deduplication and match nothing. Asking what product speaks this protocol, what the payload is attempting, and whether it resembles a known vulnerability replaces twenty minutes of searching. It is also the right tool for attacking one's own conclusion before anything gets called a zero-day.

Honeypot data is attacker-controlled text

Feeding captured payloads to a model is prompt injection aimed straight at the analysis pipeline. Model output prints to a report and nowhere else. It never triggers a command, a query, a fetch or an alert action.

Cadence

Running it

  • Daily: read the novel-payload feed. It should be short enough to eyeball with coffee.
  • Weekly: check the port histogram. Promote at most the top three ports to real emulation, reusing existing honeypot projects rather than writing them.
  • On an execution event: stop, pull the snapshot diff and the matching packet capture, and triage before reverting.
  • Monthly: re-image. Long-lived honeypots accumulate other people's implants.

Where the build departed from this plan

  • A systemd timer replaced cron. The crontab write went through without error and left an empty crontab. A timer is one file, and the rest of the system is already systemd units.
  • Python replaced jq for the rollup. First-seen tracking and payload normalization are a few lines of Python and an ugly sprawl of jq. The log format is unchanged, so jq still works for ad-hoc queries.
  • The rollup re-reads both logs in full every run. Fine at current volume, and the obvious thing to replace with offset tracking when a run stops finishing in a minute.
  • The redirect covers IPv4 only. The box has a v4 address; add an equivalent ip6 nat table if a v6 address is ever assigned.

Deliberately not built

Recorded so nobody rebuilds them out of habit. Interaction emulation beyond banners, a real-time dashboard, a database, alerting, geolocation and network-owner enrichment, packet-capture retention past triage, and machine-learning payload clustering. Each is added only when its absence is what actually blocks the work: emulation when a port shows sustained volume and truncation is losing the interesting half, clustering when the novel feed outgrows a daily read.

Phases 0–2 live since 9 September 2026. Phase 3 waits on an isolation layer. Egress stays denied; open it only through hp-egress, and close it in the same command.
