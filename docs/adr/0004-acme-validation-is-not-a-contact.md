# ACME validation is not a Contact

Issuing a certificate for a Bait Name makes Let's Encrypt fetch
`/.well-known/acme-challenge/...` under that exact Name, from several vantage
points. Those requests satisfy the definition of a Contact precisely -- a remote
Actor arriving by a Name it could not derive from the address -- and they are
our own certificate request arriving back at us.

The first issuance produced five, from five distinct addresses, in the four
seconds before the certificate entered the CT logs. Left in, they would have
been the earliest Contacts on record, and every renewal would add five more.

Requests whose path is under the ACME challenge prefix no longer count as a
Contact, nor toward the Names table.

## Consequences

This is measurement contamination generated by the instrument itself, and it was
only visible because the first Contact was timestamped *before* the certificate's
own SCT. Any future mechanism that causes traffic to arrive by a Bait Name --
uptime monitoring, a CDN health check, our own probes -- needs the same
treatment, and the same tell: a Contact that precedes the thing it should follow.
